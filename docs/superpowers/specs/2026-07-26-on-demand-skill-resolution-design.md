# On-demand skill resolution — design

**Date:** 2026-07-26
**Status:** implemented

> Revised after implementation. Three things the original design got wrong are
> corrected in place and called out in **Implementation deltas** at the end.

## Problem

A cue profile materializes a fixed set of skills at launch. When a task needs a
capability that lives in one of the other ~450 library skills, four things go
wrong at once:

1. **Recall.** `smart-loader-suggest.sh` only fires when a prompt token is
   literally a skill *name* or *category* (length ≥ 4). "coolify" works; "a
   fizetés nem megy az adminban" never reaches the matcher, so
   `stripe-best-practices` is never surfaced.
2. **Fidelity.** A soft load is `Read SKILL.md`. The skill's MCP servers, slash
   commands, and hooks don't come with it — a skill that depends on an MCP
   arrives half-working, and nothing says so.
3. **Promotion.** Loading the same skill in the same repo ten times leaves no
   trace. `cue loadout keep` exists but only covers skills the project loadout
   deferred, not the library at large.
4. **Noticing.** The reactive path rests on one soft persona rule in `core`
   ("topic mentions a tool NOT in the loaded skills list → `/smart-loader`").

All four share a root cause: cue has a static materialization step and a bag of
heuristics, but no *skill-resolution layer*.

## Non-goals

- **Hot-loading MCP servers.** A running Claude session freezes its MCP set at
  boot. We never fake it; we report what's missing and hand back the exact
  `cue summon` re-exec.
- **Autonomy.** Resolution suggests; it never injects a skill body or edits a
  loadout on its own. (Decided with the user: *"ajánl, de ne csináld."*)
- **Replacing `smart-lookup.sh`.** Its scoring is already good — multi-keyword,
  trigger/tag/description/body weighted, fuzzy + embedding fallback,
  `mcp_status`, `--exclude-loaded`. The bug is the gate in front of it.

## Architecture — a three-tier resolution ladder

```
user prompt
   │
   ├─ Tier 1  smart-loader-suggest.sh   (bash, <200ms p95, every prompt)
   │     index.json → phrase+term gate → smart-lookup.sh → "💡" block
   │     miss → exit 0, silent
   │
   ├─ Tier 2  cue resolve <query>       (TS, on demand — never on the hook path)
   │     full scoring + fidelity diff + journal append
   │
   └─ Tier 3  cue resolve --deep        (LLM, opt-in, cached)
         only after Tier 1+2 miss. Never reached from the hook.
```

The tiers are ordered by cost, and each is a strict superset of the previous in
capability. Tier 1 must stay cheap because it runs unconditionally; Tier 3 may
cost a round-trip because a human or Claude asked for it explicitly.

## Component 1 — the index (`catalog/index.json`, schema 2.2)

`catalog.json` is generated by `resources/skills/scripts/rebuild-catalog-local.sh`
(bash + jq, 219 lines). We do **not** modify it — adding capability inference to
that script means reimplementing a TypeScript parser in awk. Instead
`index.json` is a *derived* artifact built from it in TypeScript.

Per entry, `index.json` carries everything `catalog.json` has plus:

| Field | Source | Before → after |
|---|---|---|
| `triggers[]` | `parseSkillFromContent` — explicit frontmatter **plus** quoted phrases mined from the description prose | 122 → **353**/452 |
| `capability` | `parseSkillFromContent` — explicit `capability:` or inferred from description | 0 → **448**/452 |
| `notFor` | `parseSkillFromContent` — anti-scope, used as a **negative** score | absent |
| `requires.mcps[]` | `depsFromContent` (explicit `requires_mcps:` + implicit body refs) | 0 → **30**/452 |
| `quality` | `parseSkillFromContent` grade — lets the linter see index-readiness | absent |
| `mcpProviders` | which profiles declare each MCP — makes the fidelity fix command real | absent |

353, not ~450: about a hundred skills write descriptions with no quoted phrases
at all, so there is nothing to mine. Those still get a `capability`, and are
still reachable through tags and description terms.

`buildIndex` takes ~110ms over the full tree and `index.json` is ~432K — it
ships next to `catalog.json` (both live in the `resources/skills` submodule) so
a fresh clone has Tier 1 recall without running a build step.

**The index is the contract between all three tiers.** Bash reads it, TypeScript
reads it, and the Tier 3 LLM prompt is built from it. That is what makes the
query engine replaceable later without touching the other tiers.

Staleness: `index.json` is rebuilt when its mtime is older than `catalog.json`'s.
Tier 1 rebuilds nothing — if the index is missing or stale it degrades to the
current name-only behavior rather than paying a build cost on the prompt path.

## Component 2 — Tier 1 gate (`smart-loader-suggest.sh` rewrite)

Today the hook builds `vendor-keywords.txt` from `name` + `category` and exits
when no prompt token matches. The rewrite keeps the shape — cached index,
mtime invalidation, per-session throttle, `exit 0` always — and changes only
what goes into the cache:

- `phrases.idx` — `phrase<TAB>id`, from `triggers[]`. Matched with `grep -oFf`
  against the lowercased prompt. Multi-word, so this is where "find EU tenders"
  and "közbeszerzés" land. **Weight 10.**
- `terms.idx` — `term<TAB>id<TAB>field`, from name (4), category (4), tags (3),
  capability + description terms (1), stopword-filtered, length ≥ 4.
- `notfor.idx` — `term<TAB>id`, from `notFor`. **Weight −4.**

Score = weighted sum over matched terms and phrases, ×1.5 when ≥2 distinct
prompt tokens hit the same skill.

Candidates above threshold then go to **`smart-lookup.sh --annotate`**, a new
fast path that answers only "is it loaded" and "are its MCPs available" for ids
it is handed, reading just those SKILL.md files. Its ordinary search path greps
every SKILL.md body per token and scores candidates in a bash loop — measured at
**~6s on this tree**, thirty times the entire hook budget. The original design
called that path; measurement killed it. `smart-lookup.sh` still owns the
loaded-set and MCP logic, so nothing is duplicated — it is just no longer asked
to do the finding.

Measured end to end: **min 100ms / median 116ms / max 152ms** over 12 runs.

Terms are plural-folded (`webhooks` → `webhook`) by the same `tokenize()` the
index build uses. The fold is ASCII-only: a trailing "s" marks a plural in
English but not in Hungarian, where folding would turn `közbeszerzés` into
`közbeszerzé` and destroy the match. The hook re-implements this in awk because
it cannot call into TypeScript; a test asserts the two agree behaviourally,
since silent divergence here is exactly the bug class this feature exists to fix.

Output gains two lines per hit:

```
💡 Available skills (not in the `google-ads` profile):
   - deployment/coolify
     deploy backend, env vars, restarts, logs
     ⚠️ needs MCP `coolify` (not loaded) → full fidelity: cue summon coolify
     ↑ resolved 3× in this directory — keep it: cue loadout keep deployment/coolify
```

## Component 3 — Tier 2 (`cue resolve`)

```
cue resolve <query...> [--json] [--deep] [--limit N] [--rebuild] [--no-journal]
```

- **Scoring** — the same weights as Tier 1, without the bash ceiling: phrase
  matching, `category` boost, `links[]` expansion so companion skills surface
  together.
- **Fidelity** — diff the hit's `requires.mcps` against the active profile's
  resolved MCP registry. Report what is missing and the exact command that
  fixes it. Never claims an MCP is available when it isn't.
- **Journal** — append to `~/.config/cue/skill-resolve.jsonl`.
- **`--json`** — consumed by `meta/smart-loader`, mirroring `cue summon --json`.

The hook does **not** shell out to `cue resolve` — a bun process spawn (~50–100ms)
would eat half the latency budget. Claude calls it; the hook does not.

## Component 4 — Tier 3 (`cue resolve --deep`)

Reuses `skill-subset.ts`'s `claude --print` spawn and its on-disk cache, keyed
by `(query, index hash)`. Fail-open in the strict sense: any error, timeout, or
unparseable reply returns the Tier 2 results rather than an error. Off unless
`--deep` is passed.

## Component 5 — promotion

Read-side only, per the autonomy decision. `~/.config/cue/skill-resolve.jsonl`
follows the `combo-history.ts` precedent: local, **telemetry-independent**, no
consent gate, best-effort append — so "remember what I loaded here" works out
of the box. (`analytics.jsonl` is gated on `cue telemetry enable`, which would
silently disable promotion for most users.)

One line per resolution: `{ts, id, cwd, profile, tier, score}`. When Tier 1 is
about to print a skill with ≥3 entries for the current cwd, it appends the
`cue loadout keep` line. Nothing is ever written to a profile automatically.

## Error handling

Every tier fails open, and none is a gate:

| Failure | Behavior |
|---|---|
| `index.json` missing/corrupt | Tier 1 falls back to the current name-only keyword gate |
| `catalog.json` missing | hook `exit 0`, silent (unchanged from today) |
| `cue resolve` with no index | tells the user to run `cue resolve --rebuild` |
| Tier 3 timeout / bad reply | returns Tier 2 results |
| Journal write fails | ignored; resolution still returns |

## Testing

- **Index build** — every entry with a readable `source` gets a non-empty
  `triggers[]`; asserts a floor well above the 122/452 baseline so a parser
  regression is caught.
- **Scoring** — table test mapping prompt → expected top skill, seeded with the
  real misses that motivated this work (Hungarian and English).
- **Tier 1 latency** — the built index scored against a prompt stays under
  200ms on the full 452-entry set.
- **`cue resolve --json`** — output shape fixture.
- **Fail-open** — one test per tier against a corrupt/missing index.

Result: 56 tests across `catalog-index.test.ts`, `skill-resolve-journal.test.ts`
and `smart-loader-suggest.hook.test.ts`; full suite 1705 pass / 0 fail;
`tsc --noEmit` clean.

## Implementation deltas

Four things the design got wrong, corrected above:

1. **Tier 1 could not call smart-lookup's search path.** The design assumed it
   was cheap because the old hook already called it. It isn't — ~6s. The old
   hook got away with it only because its name-only gate almost never fired, so
   the cost was invisible. Fixing the gate exposed it. Resolved by adding
   `--annotate` to smart-lookup rather than duplicating its logic in the hook.

2. **Matching needed plural folding.** "webhook" in a prompt did not match
   "webhooks" in a description, which kept real matches under the threshold.
   The fold has to be ASCII-gated or it corrupts Hungarian terms.

3. **The fidelity fix command was wrong.** It suggested `cue summon <category>`,
   but categories and profiles are different namespaces — `cue summon deployment`
   names no profile. Now resolved from a precomputed `mcpProviders` map, and
   omitted entirely when no profile declares the MCP.

4. **The classifier's answers were being thrown away.** Tier 3's first live run
   returned `deep pass unavailable`. The classifier had in fact answered — with
   `KEEP: 1, 3, 10, 12`. `buildPrompt` renders a *numbered* list, which invites a
   positional reply, but `parseClaudeKeep` only accepted literal skill ids and
   filtered every number out, yielding a parse failure.

   This is a pre-existing bug in `skill-subset.ts`, not a Tier 3 one: the same
   path backs `cue launch`'s smart-subset, where the failure is invisible —
   it degrades to "kept all skills", which looks exactly like the classifier
   being unavailable. Fixed once, in `parseClaudeKeep`, which now accepts ids,
   1-based positions, or a mix.

## Verification

All three tiers exercised end to end:

| Tier | Check | Result |
|---|---|---|
| 1 | Hungarian prompt with no skill name in it | surfaces `stripe/*`, `eu-funding/*` |
| 1 | latency, 12 runs | min 100ms / median 116ms / max 152ms |
| 2 | `cue resolve --json`, fidelity, promotion counter | correct MCP + `cue summon coolify` |
| 3 | live `--deep` | `4/25 skills kept` with a reason |
| 3 | no reachable claude binary | `deep pass unavailable`, Tier 2 results |
